[SPEC] 035 — Extract `useRolePanel` + `RoleResultsPanel`: provable-by-construction data isolation, zero visible change

- **Objective**: Refactor `App.tsx`'s single-role state slice (`rows`, `status`, `errorMessage`, `haveSkillKeys`, `topGaps`, `selectedGroup` + the `loadRoleProfile`/`runGapPipeline` functions) into a reusable custom hook `useRolePanel(role: string)` that owns that entire slice internally, and extract the existing results-column JSX for one role (head chips/donut/narration/breakdown/matrix/table — whatever `App.tsx` currently renders per role) into a new `RoleResultsPanel` component consuming that hook's return shape as props. `App.tsx` is rewired to call the hook and render the panel exactly once (today's single-role UI), with **no visible or behavioral change** — this is the walking-skeleton step that proves the reusable unit works before spec 036 instantiates it 2–3 times.
- **Inputs/Outputs**:
  - `useRolePanel(role: string): { status: Status; rows: RoleSkillRow[]; errorMessage: string; haveSkillKeys: Set<string> | undefined; topGaps: ReturnType<typeof narrateTopGaps> | undefined; selectedGroup: string | null; setSelectedGroup: (g: string | null) => void; submitResume: (resumeText: string) => void; loadRole: (role: string) => void }`. Internally: a `useEffect` keyed on `role` calls `fetchRoleSkillProfile` (unchanged); a per-instance `useRef` request-generation counter, bumped on every effect run, discards a resolved fetch if the counter has since moved on — this is what prevents an old role's slow response from landing after the slot has already moved to a new role, the exact hazard Pine named, guarded per hook instance rather than per shared key.
  - `submitResume(text)` is the hook-instance-local equivalent of today's `runGapPipeline`: reads only this instance's own `rows`, calls the existing `computeSkillGap`/`narrateTopGaps` (unchanged, unmoved) and writes only this instance's own `haveSkillKeys`/`topGaps`.
  - `RoleResultsPanel` props: exactly the hook's return shape plus `role: string`, `selectedSeniority`, `theme`-independent — a pure presentational wrapper, no new state, no new derived math beyond what already exists in `App.tsx` today (donut counts, `ranked`, `topMove`, `filteredRows` move into the panel verbatim).
  - `App.tsx`'s mount-hydration effect (spec 034) and `handleRoleChange`/`handleResumeSubmit` call the hook's `loadRole`/`submitResume` instead of the old local functions — persistence (`localPersistence.ts`) is untouched, still reading/writing only the one slot-0 role/resumeText/seniority.
- **Design Pattern**: none — simple case. The reusable unit is a plain custom hook + component, called once here (and N times in spec 036); the variance is *how many instances*, not *what an instance does*, so multiplicity is the answer, not an indirection pattern. `Simplicity > Pattern purity`.
- **Bounded-AI boundary**: Zero LLM, zero new scoring/gap/join logic. `fetchRoleSkillProfile`, `computeSkillGap`, `narrateTopGaps` are moved, never rewritten — every `arbitrage_score`/gap/count in `RoleResultsPanel` is still the exact value the current `App.tsx` renders, just relocated. No cross-role computation of any kind is introduced by this SPEC (that's explicitly deferred, see spec 036's boundary note).
- **Verification Oracle**:
  - **Primary** — `frontend/src/lib/useRolePanel.test.ts` (new, vitest + `renderHook` from `@testing-library/react`): instantiate the hook **3 times** (mirroring exactly how spec 036 will call it), each given a different role, with `fetchRoleSkillProfile` mocked per-role and resolved **out of order** (e.g., instance 2's promise resolves before instance 0's, and instance 0's role is changed again before its own first fetch resolves). Assert each instance's `rows`/`haveSkillKeys` reflect only its own most-recent role's stubbed data — never another instance's data, and never a stale pre-change value. This file does not exist yet, so it is a genuine red (missing module) until Redwood builds `useRolePanel`.
  - **Regression net** — re-run the full existing suite unmodified: `frontend/e2e/leverage-table.spec.ts`, `frontend/e2e/seniority-framing.spec.ts`, `frontend/e2e/skill-group-breakdown.spec.ts`, `frontend/e2e/persistence.spec.ts` (all declared profiles), plus `frontend/src/App.test.tsx`/`App.persistence.test.tsx` — must stay 100% green with no locator changes, proving the extraction is byte-identical in behavior.
- **UI Scope**: N/A — this is a non-UI refactor task (Redwood), not a Magnolia task; zero pixels change.
- **Intellectual Control**: Isolation is proven **by construction**, not by convention: each `useRolePanel` call is a lexically distinct closure over its own `useState`/`useRef` calls — there is no shared array/map keyed by role name or slot index that a future bug could index incorrectly, and no setter any other instance could accidentally call. This is the strongest available answer to the silent-corruption risk in the routing brief, and it is proven here, before spec 036 exposes 3 of these on screen at once.
- **Constraints**: No new dependency. Mount-hydration behavior (spec 034) must be preserved exactly — the existing `didRunMountFetch` guard still fires once, still calls the hook's `loadRole`/`submitResume` for slot 0 only.
- **Edge Cases**: Role changed to `''` (cleared) — hook resets to idle/empty rows exactly as `loadRoleProfile` does today. A fetch error after a role has already been changed again — discarded by the same request-generation guard, never surfaces an error message for a role the slot has moved on from.
