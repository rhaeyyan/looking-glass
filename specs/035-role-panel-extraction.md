[SPEC] 035 — Extract `useRolePanel` + `RoleResultsPanel`: provable-by-construction data isolation, zero visible change

- **Objective**: Refactor `App.tsx`'s single-role state slice (`rows`, `status`, `errorMessage`, `haveSkillKeys`, `topGaps`, `selectedGroup` + the `loadRoleProfile`/`runGapPipeline` functions) into a reusable custom hook `useRolePanel(role: string)` that owns that entire slice internally, and extract the existing results-column JSX for one role — **as it exists today, post-spec-033/037: the two sibling cards `standing-root` (role heading, tags, `SeniorityFraming`, and, when analyzed, the donut + `TopGapNarration`/no-gaps status) and `evidence-root` (`SkillGroupBreakdown`, `FilterStatusBar`, `SkillMatrix`, `SkillLeverageTable`)** — into a new `RoleResultsPanel` component consuming that hook's return shape as props. `App.tsx` is rewired to call the hook and render the panel exactly once (today's single-role UI), with **no visible or behavioral change, including the two `aria-label`s spec 037 added** (`"Skill gap result"` on the no-gaps status paragraph, `"Skill filter status"` on `FilterStatusBar`'s root) — these must be preserved verbatim, not just their visible text. This is the walking-skeleton step that proves the reusable unit works before spec 036 instantiates it 2–3 times.
- **Inputs/Outputs**:
  - `useRolePanel(role: string): { status: Status; rows: RoleSkillRow[]; errorMessage: string; haveSkillKeys: Set<string> | undefined; topGaps: ReturnType<typeof narrateTopGaps> | undefined; selectedGroup: string | null; setSelectedGroup: (g: string | null) => void; submitResume: (resumeText: string) => void; loadRole: (role: string) => void }`. Internally: a `useEffect` keyed on `role` calls `fetchRoleSkillProfile` (unchanged); a per-instance `useRef` request-generation counter, bumped on every effect run, discards a resolved fetch if the counter has since moved on — this is what prevents an old role's slow response from landing after the slot has already moved to a new role, the exact hazard Pine named, guarded per hook instance rather than per shared key.
  - `submitResume(text)` is the hook-instance-local equivalent of today's `runGapPipeline`: reads only this instance's own `rows`, calls the existing `computeSkillGap`/`narrateTopGaps` (unchanged, unmoved) and writes only this instance's own `haveSkillKeys`/`topGaps`.
  - `RoleResultsPanel` props: exactly the hook's return shape plus `role: string`, `selectedSeniority`, `theme`-independent — a pure presentational wrapper, no new state, no new derived math beyond what already exists in `App.tsx` today (donut counts, `ranked`, `topMove`, `scoredCount`, `filteredRows` move into the panel verbatim). It renders **both** `standing-root` and `evidence-root` as its two top-level sibling outputs (matching `.lg-results`'s existing "each card is one direct child" assumption from spec 033 — `App.tsx` renders `<RoleResultsPanel .../>` where it previously rendered the two `hasRows &&` blocks directly, and `.lg-results`'s `gap: 22px` behavior is unaffected since a component returning a fragment of two card siblings preserves the same direct-child structure). `FilterStatusBar`'s `onClear`/`selectedGroup`/`filteredCount`/`totalCount` wiring moves into the panel unchanged — it is still driven by the panel's own `selectedGroup` state, nothing new.
  - `App.tsx`'s mount-hydration effect (spec 034) and `handleRoleChange`/`handleResumeSubmit` call the hook's `loadRole`/`submitResume` instead of the old local functions — persistence (`localPersistence.ts`) is untouched, still reading/writing only the one slot-0 role/resumeText/seniority.
- **Design Pattern**: none — simple case. The reusable unit is a plain custom hook + component, called once here (and N times in spec 036); the variance is *how many instances*, not *what an instance does*, so multiplicity is the answer, not an indirection pattern. `Simplicity > Pattern purity`.
- **Bounded-AI boundary**: Zero LLM, zero new scoring/gap/join logic. `fetchRoleSkillProfile`, `computeSkillGap`, `narrateTopGaps` are moved, never rewritten — every `arbitrage_score`/gap/count in `RoleResultsPanel` is still the exact value the current `App.tsx` renders, just relocated. No cross-role computation of any kind is introduced by this SPEC (that's explicitly deferred, see spec 036's boundary note).
- **Verification Oracle**:
  - **Primary** — `frontend/src/lib/useRolePanel.test.ts` (new, vitest + `renderHook` from `@testing-library/react`): instantiate the hook **3 times** (mirroring exactly how spec 036 will call it), each given a different role, with `fetchRoleSkillProfile` mocked per-role and resolved **out of order** (e.g., instance 2's promise resolves before instance 0's, and instance 0's role is changed again before its own first fetch resolves). Assert each instance's `rows`/`haveSkillKeys` reflect only its own most-recent role's stubbed data — never another instance's data, and never a stale pre-change value. This file does not exist yet, so it is a genuine red (missing module) until Redwood builds `useRolePanel`.
  - **Regression net** — re-run the full existing suite unmodified: `frontend/e2e/leverage-table.spec.ts`, `frontend/e2e/seniority-framing.spec.ts`, `frontend/e2e/skill-group-breakdown.spec.ts`, `frontend/e2e/persistence.spec.ts`, **and `frontend/e2e/results-column-restructure.spec.ts`** (all declared profiles: `desktop-light`, `desktop-dark`, `mobile-touch-dark`, `mobile-touch-light` — this file directly asserts the Standing/Evidence two-card structure `RoleResultsPanel` now owns, so it is the most load-bearing regression check for this specific extraction) — plus `frontend/src/App.test.tsx`/`App.persistence.test.tsx`, **specifically including the two spec-037-authored assertions by name** (`renders no narration region at all before any resume has been submitted` and `renders a distinct, positive role="status" message (never a blank or stale region) when narrateTopGap returns null`, both querying by the exact locked names `'Skill gap result'`/`'Skill filter status'`) — these two are the most fragile regression surface post-037 since they query by accessible name rather than structure, and must stay green with zero locator changes, proving the extraction is byte-identical in behavior, not just visually similar.
- **UI Scope**: N/A — this is a non-UI refactor task (Redwood), not a Magnolia task; zero pixels, zero accessible-name changes.
- **Intellectual Control**: Isolation is proven **by construction**, not by convention: each `useRolePanel` call is a lexically distinct closure over its own `useState`/`useRef` calls — there is no shared array/map keyed by role name or slot index that a future bug could index incorrectly, and no setter any other instance could accidentally call. The Standing/Evidence two-card split (spec 033) and the aria-label fix (spec 037) are both purely presentational concerns living inside `RoleResultsPanel`'s render output — they do not touch, and are not touched by, the isolation guarantee, which lives entirely in `useRolePanel`. This is the strongest available answer to the silent-corruption risk in the routing brief, and it is proven here, before spec 036 exposes 3 of these on screen at once.
- **Constraints**: No new dependency. Mount-hydration behavior (spec 034) must be preserved exactly — the existing `didRunMountFetch` guard still fires once, still calls the hook's `loadRole`/`submitResume` for slot 0 only.
- **Edge Cases**: Role changed to `''` (cleared) — hook resets to idle/empty rows exactly as `loadRoleProfile` does today. A fetch error after a role has already been changed again — discarded by the same request-generation guard, never surfaces an error message for a role the slot has moved on from. **Forward-pointer, not this spec's problem**: spec 037's two `aria-label`s were named uniquely on the assumption of exactly one mounted panel; spec 036 will mount up to 3 `RoleResultsPanel` instances simultaneously, each carrying the identical labels (`"Skill gap result"`, `"Skill filter status"`, `"Loading skill profile"`, `"No skills found for this role"`), which will collide across panels exactly as spec 037 fixed within one panel. This SPEC does not need to address it (only one instance ever renders here), but spec 036 must, explicitly (e.g. per-panel-qualified accessible names) — flagged now so it isn't rediscovered as a fresh a11y bug during 036's audit.
