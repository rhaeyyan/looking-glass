[SPEC] 038a — `useRolePanel`: split `submitResume` into extraction + confirmation phases

- **Objective**: Change `submitResume(resumeText)` to run only `extractResumeSkills` and store the result as a new returned field `pendingConfirmation: { rows: RoleSkillRow[]; autoDetectedKeys: Set<string> } | undefined`, without touching `haveSkillKeys`/`topGaps`. Add `confirmSkills(checkedSkillKeys: Set<string>): void` — re-slices `rows` by the checked keys, hands the resulting `skill_name_raw` list to the existing, unmodified `computeSkillGap`, sets `haveSkillKeys`/`topGaps`, clears `pendingConfirmation`. Add `cancelConfirmation(): void` — discards the draft, returns to un-analyzed idle (resume text stays in the caller's textarea for re-edit/resubmit). `loadRole`/a fresh `submitResume` while a `pendingConfirmation` is outstanding discards the stale draft (extends the existing request-generation-guard rationale) so a slow-edited draft can never get confirmed against a role the slot has since moved off of.
- **Design Pattern**: none — simple case.
- **Bounded-AI boundary**: Zero LLM, unchanged. `extractResumeSkills`/`computeSkillGap` are moved-into, never rewritten; `confirmSkills` performs no scoring itself — it is pure re-slicing of already-fetched rows by a user-chosen key set.
- **Verification Oracle**: `frontend/src/lib/useRolePanel.test.ts` (extend) — `submitResume` populates `pendingConfirmation.autoDetectedKeys` matching `extractResumeSkills`'s own output for a fixture vocabulary/resume and leaves `haveSkillKeys` undefined; `confirmSkills` with an edited set (un-checking a row extraction wrongly matched, checking one it missed) produces `haveSkillKeys`/`topGaps` reflecting the edited set, not the auto-detected one; confirming without touching any checkbox reproduces today's pre-this-spec output byte-for-byte (regression net); `loadRole` while a draft is pending clears it without leaking into the new role.
- **Intellectual Control**: Extends spec 035's per-instance-closure isolation guarantee rather than introducing a second call site that could drift from it.
- **Constraints**: No new dependency; `extractResumeSkills`/`computeSkillGap` themselves untouched.
- **Edge Cases**: role/text unchanged, checklist untouched, confirm → identical output to current behavior. `submitResumeAutoConfirm` reproduces today's synchronous output exactly and is a permanent function, not deleted once 038b lands — it becomes compare mode's steady-state call path unless a future `/grill-me` on compare-mode confirmation decides otherwise.
- **Amendment (post-build)**: Building this SPEC broke `App.tsx`'s three existing `submitResume` call sites — they relied on the old single-step synchronous behavior to display results immediately, and nothing in this SPEC's original scope re-wires them. Resolved by adding one new permanent export, **`submitResumeAutoConfirm(resumeText: string): void`**, which runs extraction and immediately computes/sets `haveSkillKeys`/`topGaps` in one synchronous step (exactly what `submitResume` used to do inline), bypassing `pendingConfirmation` entirely. `App.tsx` is added to this SPEC's file list for a **mechanical rename only** — the three `panels[N].submitResume(resumeText)` calls plus the mount-hydration call become `panels[N].submitResumeAutoConfirm(resumeText)`. Zero new logic, zero visible/behavioral change; this is what keeps `main` green with 038a alone. `useRolePanel.test.ts` gets one corresponding case asserting `submitResumeAutoConfirm` reproduces today's exact single-step output.
- **Files**: `frontend/src/lib/useRolePanel.ts` (Redwood), `frontend/src/lib/useRolePanel.test.ts` (Cypress, red first), `frontend/src/App.tsx` (Redwood — mechanical rename only, added by amendment above).
- **Tipping Point**: unchanged from spec 035 — a 4th non-`App.tsx` caller promotes this out of `lib/`.
