[SPEC] 038b — Skill-confirmation checklist UI + persistence v2 (single-panel mode only)

- **Objective**: Between submit and analyzed results (single-panel/`compareMode === false` only), render every vocabulary skill as a checkbox, pre-checked per `pendingConfirmation.autoDetectedKeys`, with a confirm action calling `confirmSkills` and a back action calling `cancelConfirmation`. Bump `localPersistence.ts`'s key `lookingglass:v1:state → lookingglass:v2:state`, add `confirmedSkillKeys: string[] | null` plus a fingerprint of the `resumeText`+`role` pair it was confirmed against. On rehydration: fingerprint matches → call `confirmSkills` directly (skip the checklist); fingerprint mismatch/absent → fall back to `submitResume`'s existing (now checklist-first) behavior. An old `v1` blob is discarded exactly like any other unrecognized schema (v1 never shipped confirmation semantics, so there is nothing safe to migrate).
- **Design Pattern**: none — simple case.
- **Bounded-AI boundary**: Zero new computation — pure presentation of, and persistence for, a user's own explicit choice.
- **Verification Oracle**: `frontend/e2e/skill-confirmation.spec.ts @ desktop-light`, `@ mobile-touch-dark` (new) — submit a resume against a fixture vocabulary, assert every vocabulary skill renders with the correct pre-checked state, toggle one off/one on, confirm, assert the donut/topGaps/table reflect the edited set (not raw auto-detection); reload and assert the confirmed set redisplays without a fresh checklist. `frontend/src/lib/localPersistence.test.ts` (extend) — v2 round-trip, fingerprint-mismatch discard, stale-`v1`-blob discard.
- **UI Scope**: structural — a new checklist step's DOM, not a styling tweak to the existing layout.
- **Intellectual Control**: A confirmed set is treated as user input, not cached score — consistent with spec 034's line, extended to a new input type rather than violated.
- **Constraints**: No new dependency. **Amended per 038a's post-build resolution**: `App.tsx` post-038a calls `submitResumeAutoConfirm` for all three panels (a permanent function reproducing today's synchronous auto-confirm behavior, not a temporary shim). This SPEC's `App.tsx` edit changes **only the single-panel (`compareMode === false`, `panels[0]`) call site** from `submitResumeAutoConfirm` back to the real split (`submitResume` → checklist UI → `confirmSkills`). `panels[1]`/`panels[2]` (compare mode) keep calling `submitResumeAutoConfirm`, unchanged — compare mode is therefore never visibly broken or unimplemented while the compare-mode confirmation UX question is still pending a dedicated extension SPEC, and this also already matches one of the four options considered for that question ("compare mode keeps raw auto-detection, confirmation is single-panel-only") as a live default, not a placeholder.
- **Edge Cases**: edited `resumeText` or changed role after a confirmation invalidates the persisted set via fingerprint mismatch — never silently reapplied to new input.
- **Files**: `frontend/src/lib/localPersistence.ts` (Redwood), `frontend/src/lib/localPersistence.test.ts` (Cypress, red first), `frontend/src/components/matrix/SkillConfirmationChecklist.tsx` (new, Magnolia), `frontend/src/App.tsx` (edit, Magnolia), `frontend/e2e/skill-confirmation.spec.ts` (new, Cypress, red first).
- **Tipping Point**: If compare mode's confirmation extension lands, `confirmedSkillKeys` likely needs to become per-slot rather than singular — revisit `PersistedState`'s shape then, not now. **Human decision on record for that future SPEC**: compare-mode confirmation should be one checklist per active panel, shown sequentially — the user confirms panel 0's skills, then panel 1's, then panel 2's, before any panel computes its gap (not simultaneous side-by-side checklists, not a single merged-vocabulary checklist, not skipped).

```markdown
[FORCES]
1. A user's explicit correction is real input and must survive reload like resumeText does > spec 034's "never persist derived state," which was written for computed scores, not user confirmations
2. A stale/mismatched confirmed set must fail open to a fresh checklist, never silently apply to the wrong input > convenience of skipping re-confirmation
3. Simplicity > Pattern purity
```
